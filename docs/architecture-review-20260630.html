CANDIDATE A

Commit Graph Layout — from stub to deep module

Files: core_domain/src/lib.rs → new graph_layout crate
⬆ Strong
Problem

The commit graph layout algorithm is the core business value of GitCthulhu — it turns a flat list of git objects into a readable branching visualisation. Right now it is a shallow stub: three lines that assign lane: index % 3.

It lives inside core_domain, which claims "zero-dependency" in its description, but pulls in rayon for parallelism that never runs. The algorithm is invoked as a side effect inside AppState::apply_event, making it impossible to test without driving the full state machine.

Deletion test: if you delete build_dag from core_domain, does complexity concentrate? Yes — the domain has no graph topology concern; only commits and parent pointers.

Solution

Extract a graph_layout crate with a single deep interface:

pub fn layout_graph(
  commits: &[Commit],
) -> Vec<DagNode>

Pure function — no state, no side effects, no async. The algorithm (topological sort, graph colouring for lanes, edge routing) develops and verifies in isolation. core_domain removes rayon and the build_dag fn. AppState holds dag_nodes as a derived field set by the application layer after calling layout_graph.

Benefits — Locality & Leverage
  • Locality: All graph layout logic in one place. Reading it requires no understanding of the state machine.
  • Leverage: A pure function is trivially fuzzable and property-testable — throw 10,000 commit graphs at it. Currently zero tests cover layout.
  • Depth: The interface (&[Commit] → Vec<DagNode>) hides topological sort, DFS, lane-colouring — complex implementation behind a minimal interface.
  • Production unblock: The stub produces nonsensical lane assignments for any real repository. This is the most user-visible gap.

CANDIDATE B

gui_app direct adapter coupling — honour the seam

Files: gui_app/src/main.rs + new compositor module
⬆ Strong
Problem

GitApp holds adapter: GitoxideAdapter — a concrete type — not Box<dyn GitRepository>. The port exists. The seam is drawn. But the GUI bypasses it by importing git_adapter directly.

Default::default() constructs the adapter with a hardwired path: GitoxideAdapter::new("."). There is no way to open a different repository at runtime, no way to swap in a mock for tests, and no way to support multiple repositories. This is a hypothetical seam — one adapter exists, so the trait does no real work yet.

Solution

Introduce a compositor module that constructs adapters and injects them through ports:

struct GitApp {
  repo: Box<dyn GitRepository>,
  creds: Box<dyn CredentialStore>,
  config: Box<dyn ConfigStore>,
}

The compositor (in main.rs or a composer.rs) wires GitoxideAdapter, NativeKeyring, ConfyConfigStore and passes them in. gui_app's Cargo.toml drops its git_adapter dependency — it only knows about core_domain ports.

Benefits — Locality & Leverage
  • Testability: GUI logic can be tested with an in-memory MockGitRepository that returns canned commits. Right now, zero GUI tests are possible.
  • Seam becomes real: When two adapters exist the trait does work. Currently it is speculative — one adapter = hypothetical seam.
  • Runtime repo selection: Enables "File → Open Repository" by re-injecting a new adapter after construction.
  • Depth: gui_app stops knowing about adapter construction. Leverage: all adapter wiring in one compositor.

CANDIDATE C

AppState — decompose the God state machine

Files: core_domain/src/lib.rs lines 175–245
⬆ Strong
Problem

AppState is one struct spanning: app lifecycle phases, repository session data, authentication flow, settings, config, repository path, and computed DAG geometry. Ten fields, one state machine.

Critical friction: handle_token_received calls store.save_token() — an OS keyring write — inside what should be a pure state transition. The state machine is impure. You cannot replay events in tests without wiring up a real keyring. This is the testability equivalent of doing a database write inside a domain model constructor.

Solution

Separate into three focused types:

TypeResponsibility
RepoSessionCommits, branches, diff, current branch
AuthFlowOAuth/SSH state — pure transitions only
AppPhaseLoading / Ready / Error lifecycle

Side effects move to a command handler. apply_event(state, event) → (State, Vec<SideEffect>) — pure. The application runner executes side effects after each transition.

Benefits
  • Purity: A pure state machine is trivially testable — feed it events, assert on output state. No keyring, no network required.
  • Replay: Pure state + event log = reproducible crash reports and time-travel debugging.
  • Locality: Auth state bugs live in AuthFlow. Repo display bugs in RepoSession. No cross-concern grep.
  • Leverage: The SideEffect enum becomes a seam — mock it in tests, execute it in production.

CANDIDATE D

DomainError::Unknown(String) — error taxonomy erosion

Files: core_domain/src/lib.rs (DomainError enum) · all 6 adapters
● Worth exploring
Problem

Every adapter maps errors to DomainError::Unknown(String). All 6 adapters do this. The error type has NotFound and AuthenticationFailed variants — the right shape — but the implementation never reaches them. They are effectively unreachable.

The caller cannot distinguish a network timeout from a corrupt repository from a missing SSH key. Every error handler parses a string. The interface hides nothing — all information is in the opaque string. That is a shallow module: interface as complex as reaching into the implementation.

Solution

Extend DomainError with production-grade variants and use them consistently:

enum DomainError {
  NotFound(String),
  AuthenticationFailed,
  AuthExpired { provider: String },
  NetworkTimeout { url: String },
  RepositoryCorrupt { path: String },
  SshKeyNotFound { tried: Vec<String> },
  PermissionDenied { resource: String },
  Unknown(String), // last resort only
}
Benefits
  • Leverage: The GUI handles AuthExpired by showing a re-auth prompt, NetworkTimeout with retry logic — no string parsing required.
  • Tests: Assert matches!(result, Err(DomainError::SshKeyNotFound { .. })) — far more robust than asserting on an error string.
  • Locality: Each error variant signals exactly what happened. No cross-module grep for error strings in logs.
CANDIDATE E

GitRepository port — fetch seam leaks auth strategy

Files: core_domain/src/lib.rs (GitRepository trait) · git_adapter/src/lib.rs
● Worth exploring
Problem

The GitRepository port has two separate fetch methods:

fn fetch(&self, store: &dyn CredentialStore)
fn fetch_ssh(&self, ssh: &dyn SshManager)

The port knows that HTTPS uses tokens and SSH uses key files. That is transport-layer knowledge inside an abstract interface. A caller must inspect the remote URL to decide which method to call. The seam leaks the auth protocol upward.

Solution

Introduce a GitCredential enum that captures auth strategy without naming the transport:

enum GitCredential {
  Token(String),
  SshKey { path: String },
  Anonymous,
}

trait GitRepository {
  fn fetch(&self, cred: GitCredential);
}

The adapter resolves which git transport to use internally. The port stays clean. Interface shrinks from 2 methods + 2 dependency parameters to 1 method + 1 value.

CANDIDATE F

SshManager port — four concerns, one interface

Files: core_domain/src/lib.rs · ssh_adapter/src/lib.rs
● Worth exploring
Problem

SshManager is a wide port with 4 methods mixing distinct concerns:

  • get_default_key_path — key discovery (FS operation)
  • resolve_subsystem_path — WSL2 path translation (env concern)
  • prepare_ssh_env — env var construction (combines the above)
  • preflight_check — health check (spawns a process)

The port's caller only ever needs prepare_ssh_env result. The other three are the adapter's internal implementation steps exposed as a port interface — the opposite of information hiding. The interface is nearly as complex as the implementation. Deletion test: delete get_default_key_path from the port. Complexity concentrates in the adapter. That is the correct direction.

Solution

Narrow the port to what callers actually need:

trait SshManager {
  fn resolve_credential()
    -> Result<GitCredential, DomainError>;
  fn preflight_check()
    -> Result<(), DomainError>;
}

get_default_key_path, resolve_subsystem_path, and prepare_ssh_env become private methods on NativeSshManager. Port interface shrinks by 50%. Combined with Candidate E, SshManager may be eliminated entirely — NativeSshManager::resolve_credential() returns a GitCredential::SshKey, handled by git_adapter directly.

React src/ web preview — clarify or remove

Files: src/App.tsx · src/main.tsx · README.md
◇ Speculative

The src/ directory is a React/Vite app that shows a file-tree demo — it was the "sandboxed web preview" from the Google AI Studio prototype session. The project's README.md is also the AI Studio template, not documentation. The real application is the iced GUI in gui_app/.

⚠ Framework decision required before production

Is GitCthulhu a Tauri app (Rust + web frontend) or a native iced app? The current structure implies iced. If that is the answer, src/ is dead weight and should be removed, and the README.md replaced. If Tauri is the target, the architecture reversal is significant — gui_app becomes the Tauri backend and src/ becomes the real UI.

Listed here to make the ambiguity explicit. Not worth spending architectural energy on until the framework question is settled.
